# 工具中心主设计

> **落地状态（2026-07-21）**：首期已落地——`/tools` 工具中心 + 注册表 + 侧栏仅「工具中心」入口；「标签图片打包」经卡片进入 `/tools/image-link-zip`。

## 1. 目标与范围

工具中心用于承载独立、可复用的业务辅助能力，例如 Excel 文件处理、批量下载和数据校验。它解决以下问题：

- 统一发现和进入各类工具，避免侧边栏随着工具增加而变得冗长。
- 让每个工具拥有独立的页面、接口、权限和运行状态，互不影响。
- 为后续新增工具提供固定的信息架构、实现边界和文档规范。

本设计定义工具中心的公共规则；不定义某个工具的具体字段、模板或处理逻辑。此类内容必须写在对应工具的独立设计文档中。

## 2. 信息架构

### 2.1 导航

侧边栏保留一级分组“常用工具”，首期仅提供“工具中心”入口。工具中心是所有工具的默认发现页；现有及后续工具均通过工具中心卡片进入，不在侧边栏单独展示。

当工具数量和使用频率稳定后，可基于实际使用情况，将少量高频工具加入该分组作为快捷入口；此变更应同步更新本设计文档。

推荐路由：

| 页面 | 路由 | 说明 |
| --- | --- | --- |
| 工具中心 | `/tools` | 按分类浏览、搜索和进入工具 |
| 标签图片打包 | `/tools/image-link-zip` | 从 Excel 指定列读取图片链接并下载为 ZIP；通过工具中心卡片进入 |

### 2.2 工具中心页面

页面按“分类区块 + 工具卡片”组织，而不是将所有工具直接平铺在菜单中。

每张卡片包含：

- 图标、工具名称和一句话用途。
- 所属分类与适用对象。
- 主要输入和输出的简要说明，例如“Excel → ZIP”。
- 主操作“立即使用”。
- 可选状态：`新功能`、`维护中`、`无权限`。

首期分类：

| 分类 | 用途 | 首期工具 |
| --- | --- | --- |
| Excel 与文件 | 上传、解析、转换、打包文件 | 标签图片打包 |
| 数据辅助 | 校验、查询、整理业务数据 | 后续按需求新增 |

当工具数量较少时，不需要搜索、收藏或最近使用；工具达到 6 个以上后，再加入这些能力。

## 3. 页面与交互规范

### 3.1 独立工具页

每个工具使用独立路由和独立视图，不把复杂表单堆叠在工具中心首页。页面统一采用以下结构：

1. 标题与用途说明。
2. 输入区：文件、业务筛选条件、模板或选项。
3. 执行区：主按钮、校验提示和处理进度。
4. 结果区：预览、统计、下载链接或失败明细。
5. 使用说明：格式限制、数据范围和常见问题。

耗时操作必须展示处理中状态并禁止重复提交；后台任务应支持进度、失败原因和结果下载。轻量同步操作可直接返回下载文件。

### 3.2 统一体验

- 所有工具在执行前完成输入校验，错误信息应说明如何修正。
- 文件工具明确可接受的格式、大小、行数和处理上限。
- 导出类工具在执行前展示记录数或汇总预览，避免误导出大量数据。
- 结果文件使用可读的中文名称，并带生成时间；失败时保留可定位的错误信息。
- 工具不修改核心业务数据；如未来需要写入数据，必须在该工具设计中明确权限、确认步骤和审计记录。

## 4. 技术设计约定

### 4.1 前端

- 工具中心视图放在 `frontend/src/views/tools/`。
- 每个工具一个独立 Vue 视图，命名为 `<ToolName>View.vue`。
- 工具接口客户端统一放在 `frontend/src/api/tools.ts`；工具增多后可拆分为 `frontend/src/api/tools/<tool-name>.ts`。
- 路由名使用 `tools-` 前缀，路径使用 kebab-case。
- 首期侧边栏仅配置工具中心；具体工具目录由工具中心维护。

### 4.2 后端

- 工具 API 统一使用 `/api/v1/tools/` 前缀。
- 每个工具以独立服务模块封装核心处理逻辑，路由层仅负责参数校验、任务创建和响应。
- 长耗时任务提供“创建任务、查询状态、下载结果”三个能力；任务数据与临时文件应具备过期清理策略。
- 导出文件仅包含当前用户有权限访问的数据。

### 4.3 测试

- 每个工具至少覆盖核心输入校验、成功处理和失败处理。
- 文件导出工具应验证生成文件可被读取，并检查表头和关键字段。
- 涉及筛选和权限的工具应覆盖数据范围限制。

## 5. 工具注册信息

工具中心应从前端统一的工具注册表读取卡片信息，而不是在页面中散落硬编码。每项至少包含：

```ts
type ToolDefinition = {
  id: string
  name: string
  description: string
  category: 'file' | 'warehouse' | 'data'
  route: string
  icon: string
  inputSummary: string
  outputSummary: string
  status?: 'active' | 'coming-soon' | 'maintenance'
  permission?: string
}
```

注册表只管理展示与导航；工具自己的参数、模板和业务规则仍归属于独立工具页面及其设计文档。

## 6. 首期工具边界

### 6.1 标签图片打包

- 输入：Excel 文件与图片链接所在列。
- 输出：下载成功的图片 ZIP 包及成功/失败统计。
- 当前实现路由：`/tools/image-link-zip`。
- 具体接口和处理限制以现有实现及后续工具文档为准。

## 7. 后续设计文档规范

每个工具在本目录下建立独立 Markdown 文档，文件名采用 `<tool-name>-design.md`。例如：

```text
docs/design/tools/
├── tools-center-design.md
├── image-link-zip-design.md
└── <tool-name>-design.md
```

独立工具文档至少包括：

1. 业务目标和非目标。
2. 用户流程与页面交互。
3. 输入、输出、字段映射和模板示例。
4. 数据来源、筛选规则、权限和异常处理。
5. API、任务模型和文件保留策略。
6. 验收标准与测试场景。

修改某个工具时，优先更新该工具的独立文档；只有公共导航、分类、交互或技术约定变化时，才更新本主设计。

## 8. 推进顺序

1. 建立 `/tools` 工具中心与工具注册表，将现有图片打包工具接入。
2. 为每个新增工具先完成对应的独立设计文档。
3. 工具数量增长后，再实现搜索、收藏、最近使用和权限驱动展示。
